# C4 implementation notes: GitHub delivery

Phase C4 per `docs/spec/20-implementation-phases.md`. Where the specification left
something open, the simplest choice consistent with it was taken and is recorded here.
Nothing here changes the specification; proposed spec changes are listed at the end.

## What C4 adds

The GitHub App authenticator (RS256 JWT signed from the mounted key in memory,
repository-scoped installation tokens); the REST client with pagination and rate-limit
handling and every read observation needs; the publisher container (bundle verify, head
assertion, commit author and trailer check, push without force); repository registration
with the operator's external-review attestation; the `publishing` task state and the
`branch_pushed_at_head` and `pr_exists_head_matches` gates; PR observation by polling
with the optional HMAC-verified webhook accelerator; external review as cycles with
components, allowlisted logins, and completed-cycle round counting; dispositions; CI
certification with failure capture, `ci-decision`, and `head-decision`; `ready_for_merge`
and `merged` observation; `head_diverged` handling; and the wakes for all of it.

## Decisions

1. **The token leaves memory once, on stdin, into a tmpfs.** S10 established that
   `docker cp` cannot reach a tmpfs inside a `--read-only` container and that without
   `--read-only` it lands the value on the writable layer, which is disk. The publisher
   is created with `OpenStdin` and `StdinOnce`, started, and then attached to through
   the Docker API (`POST /containers/{id}/attach`), which is `docker run -i` by another
   name. The value is written to that socket and the write side is closed. It is never
   in `Env`, in `Cmd`, in a bind source, or in this process's argv.
2. **`InstallationToken` hides its own value.** `reveal()` is a method, `__repr__` and
   `__str__` never show the value, and `discard()` empties it. An accidental
   `f"{token}"` in a log line cannot leak a token, which is the failure mode the S10
   risks section names.
3. **The authenticator caches the value, not the object.** Each call returns its own
   `InstallationToken`. The first version shared one object; the publisher discarded it
   when its job ended and every later caller got an empty string and a 401. The cache
   holds a value and an expiry and issues a fresh wrapper, so "discard after use" stays
   the discipline it should be.
4. **The publisher gets the bundle and nothing else of the collector's output.** 23 says
   the bundle artifact is mounted read-only. The collector's output directory also holds
   the diff, the report copy, and a fresh tree, which are evidence the gates read, so the
   bundle is copied into `publish/<attempt>/bundle` and only that directory is mounted.
   The container holding a credential sees one file.
5. **The publisher fetches `base_ref` from the real remote, and everything else from the
   bundle.** 23 says "a fresh clone from Crucible's bare cache". The bundle is
   `base_ref..work_branch`, so it names prerequisite commits and neither `git bundle
   verify` nor `git fetch` will look at it until the repository has them. The publisher
   therefore does `git init`, fetches `base_ref` from the remote it is about to push to,
   verifies the bundle, fetches the work branch out of it, and pushes. It never reads the
   worker's tree, the worker's `.git`, or a cache a worker could have influenced, which
   is the stronger reading of the same rule. (Found live: the first version skipped the
   base fetch and `git bundle verify` failed for want of the prerequisite.)
6. **The credential helper is run through `sh`, from a git config file.** A Docker tmpfs
   is `noexec` unless `exec` is asked for, and the publisher's `/tmp` keeps `noexec`, so
   the helper cannot be executed as a file. git runs a helper value beginning with `!`
   through the shell; the value has spaces, so it lives in a git config file in the
   container's own tmpfs rather than on a command line a shell variable would
   word-split. That is the same shape the C3 preparer uses for `safe.directory`.
   (Also found live.)
7. **The credential helper checks protocol and host before answering.** S10 follow-up 6.
   A helper that answers unconditionally hands the token to whatever remote git was
   pointed at. The host it answers for is configuration (`github.credential_host`), and
   `GIT_TRACE*` and `GIT_CURL_VERBOSE` are unset inside the script rather than trusted
   to be absent, because either of them prints the Authorization header.
8. **`repositories.url` is where Crucible's containers fetch from; the push remote is
   derived from the registered name.** In production they are the same GitHub url. They
   differ in one case that matters: a private target repository, which a worker cannot
   clone because workers hold no GitHub credential (23). The live tier registers the
   repository by its `owner/name` and points `url` at a local bare mirror, so the
   preparer and the collector clone locally and the publisher still pushes to GitHub with
   the App token. `push_url_for` makes that explicit rather than implicit.
9. **The API never touches GitHub.** Acceptance moves the task to `publishing` and
   returns; the supervisor mints, pushes, and opens the PR on its next tick. That keeps
   14's rule that the API enqueues everything that touches an attempt, and it means a
   publication survives an API restart.
10. **The poll and the webhook run the same code.** `observation.py` takes an
    `Observation` snapshot and is pure of I/O; `delivery_tick.py` does the HTTP and the
    containers. A webhook delivery does not write observations of its own: it is stored
    normalized, and it makes the next poll of that pull request happen now. That is what
    23 means by "webhooks only shorten latency", and it is why a webhook cannot become a
    second source of truth with different rules.
11. **A reaction's head binding is recorded as inferred.** S12: a reaction carries no
    commit id. `external_reviews.sha_inferred` says so on the row, and
    `require_review_on_final_sha` refuses to be satisfied by a reaction at all, with that
    reason in the gate's detail.
12. **A reaction that disappears is recorded as absent, not as deleted.** Polling cannot
    see the deletion, only that the set shrank, and it cannot see a reaction created and
    deleted between two cycles. `reactions.removed_at` is the observation time, and the
    event says what it does and does not mean.
13. **A 403 on the PR-level reactions endpoint is "unobservable", recorded once.** The
    App lacks Issues read until the operator adds it. The poll continues, the flag lives
    on the pull request row, `GET /supervisor` names the repositories affected, and the
    task keeps waiting rather than failing. When the permission arrives the next poll
    recovers by itself, which an integration test asserts in both directions.
14. **Publication posts one configured external-review trigger.** When a provider and
    required rounds are configured, `request_on_publish` defaults to true and the App
    posts `trigger_comment` after recording the pull request. It records the returned
    comment identity and checks issue comments on republish. A correction never posts
    again. Whether Codex accepts an App-authored mention remains a live proof item.
15. **Closing keywords are defanged, not deleted.** The body carries the worker's
    limitations and risks as worker-asserted text. A `fixes #99` inside one of them would
    close an issue nobody authorized, so every closing keyword that precedes a reference
    is escaped with a backslash: GitHub stops acting on it and the sentence still reads.
    Only `deliverables[].closes` produces a `Closes` line.
16. **The title is refused, never rewritten.** A silently rewritten title is a claim
    Crucible did not make. The secret scan runs before the length check, so a long title
    containing a token is refused for the reason that matters.
17. **`github_deliveries` is neither fenced nor append-only.** It is written by the
    webhook endpoint, which holds no supervisor lease and has no authenticated principal,
    and it is processed by the supervisor afterwards. Its events are recorded under the
    principal `github` for the same reason: an event whose principal is `crucible` is
    fenced to the supervisor (14).
18. **A rejected delivery stores nothing, including its claimed id.** An unsigned request
    is an unauthenticated claim about everything in it. The rejection is counted as an
    event with the event name and the reason, and nothing else.
19. **Post-PR gates re-evaluate every tick, not only on a poll.** 09 asks for exactly
    that, and it is also what turns a disposition recorded through the API into progress
    without waiting for the poll interval.
20. **Work scheduled after a pull request exists runs as a `correct` execution.** 09 says
    a correction's workspace starts from the remote `work_branch` head. Once a PR exists,
    every further attempt is against that branch, so the role is `correct` whether or not
    the contract version carries a correction section. That is what makes a `recollect`
    decision resume from the divergent head rather than from `base_ref`.
21. **An empty required-check set is pending in code, not only in prose.** `certify`
    returns `pending` with the reason, and `allow_no_ci` returns `skipped`, never
    `green`. It is the rule most likely to be got wrong by an "is everything green"
    check, so it has its own unit tests in both directions.
22. **A CI re-run is recorded, never performed.** Re-running needs Actions write, which
    ADR 0007 does not grant. `ci-decision rerun` records the intent, moves the task back
    to `awaiting_ci_certification`, and wakes with reason `ci_rerun_needed`. (Superseded
    by hades #435: with Actions write on the installation Hades re-runs the failed jobs
    itself; spec 23.)
23. **Dedupe uses `RETURNING`, not `rowcount`.** An `INSERT ... ON CONFLICT DO NOTHING`
    can report an unknown row count, and "unknown" read as truthy called every repeat a
    new row. Both idempotent inserts (a delivery, a head) return the inserted key or
    nothing.
24. **The fake GitHub server is real HTTP.** The integration tier runs a fake
    api.github.com on loopback so `RestTransport` and `RestGitHubClient` are exercised,
    including pagination, the 403 on reactions, and the token hand-over. Every
    secret-shaped value in the tiers, the App key and every installation token, is
    generated at run time; nothing secret-shaped is checked in.

## The correction round

Four findings from the external reviewer on the pull request and sixteen from the
internal non-author review. What changed, beyond the fixes themselves:

25. **At-mentions are defanged like closing keywords.** A mention notifies a person,
    subscribes a team, and, for a provider whose reviewer answers its own name, triggers
    a review under whatever identity opened the pull request. 23 makes the trigger the
    orchestrator's act under the operator's account, so a mention arriving through
    worker-asserted text would be Crucible performing it instead. Every `@name` in the
    body is escaped, and a title carrying one is refused. **Backticks are not
    protection**: the provider reads the raw body, not the rendered HTML, which is how a
    quoted phrase triggered it on this phase's first pull request. The literal trigger
    phrase is not written anywhere in this repository for the same reason.
26. **The commit-policy check stops the push.** It was written and then ignored: the
    author and trailer problems were recorded and the push went ahead anyway. The script
    now refuses with its own exit code, the token goes before it does, and the problems
    reach the event, the wake, and `publish_failed`.
27. **A `fix` disposition is not "dispositioned".** 09 advances out of
    `external_feedback_received` when every comment is dispositioned *and none is fix*.
    A `fix` is Foundry saying the work is not done, and what follows it is a correction.
28. **An issue comment is not a round.** The provider posts its summary comment within
    about ten seconds of the pull request opening, minutes before any verdict, and edits
    it when the review lands (S12). Counting it completed the cycle before a verdict
    existed, and since issue comments are not in the dispositions gate the task then
    advanced to certification with no review at all. `comment` is out of the default
    `accepted_signals`, and a comment carrying the provider's summary marker is never a
    round even under a policy that accepts comments generally.
29. **A reused pull request must match the contract, not merely carry the new head.** The
    base is sent on the update, and a pull request whose base or draft flag does not match
    fails publication with the mismatch rather than advancing. GitHub does not accept
    `draft` on that endpoint, so the draft case is reported and refused rather than
    silently corrected.
30. **Advancement out of `external_feedback_received` is the dispositions gate's
    decision.** It was conditioned on the rounds gate as well, which made the "rounds
    outstanding, go back and wait" branch unreachable: `required_rounds: 2` and
    `retrigger_after_correction` could never work and the task parked forever.
    `advance_from_feedback` now chooses the branch, which is what it was written to do.
31. **Everything repository-controlled is redacted at the point it is read.** The CI log
    excerpt, the publisher's own log, and the remote's refusal message all end up in
    stored rows, and all three now pass through the scanner first.
32. **The overdue clock starts when the task entered the state it is waiting in**, from
    the transition's own event, not when the pull request was opened. A correction on a
    three-day-old pull request was "overdue" on its first poll.
33. **The webhook reads a bounded body and records nothing an unauthenticated caller
    chose.** The HMAC is over the raw body, so the body is read before it can be
    verified; the endpoint caps it at 1 MiB by `Content-Length` and by a bounded read.
    A rejected delivery's event names the claimed event only when it is one of the
    handled set, and `unrecognized` otherwise.
34. **Every observed insert is idempotent.** A duplicate in one poll batch used to raise
    and roll back the whole tick. Reviews, comments, reactions, and certifications all
    insert with `ON CONFLICT DO NOTHING RETURNING`, and the caller records the event only
    when something was actually stored.
35. **Dropping `tasks.publish_pending` moves the tasks that were using it.** A task
    accepted under C2 waits in `awaiting_acceptance` with the flag raised; the migration
    moves it to `publishing` and writes the `task_publishing` event the transition owes
    it, before the column goes.
36. **A downgrade never deletes an audit row.** The old event-kind constraint comes back
    `NOT VALID` and is not validated, so new rows obey the C3 list and the C4 rows that
    exist stay.
37. **The closer is fetched from the issue timeline.** `GET /pulls/{n}` carries
    `merged_by` and no closer, so 23's "with the closer recorded" needed a second call.
    It is best effort: a permission refusal records the close with no actor rather than
    failing the observation.
38. **`neutral` and `skipped` are not `success`.** 23 says green means every member
    concluded `success`; the first version treated both as passing, so a required check
    that was skipped certified green. They are pending now, which is what the timeout is
    for. (See the proposed spec changes: if the specification means to allow them, it
    should say so, but the code matches what it says today.)
39. **The publisher has its own egress network.** It was sharing the workers' network,
    whose proxy permits every model endpoint a harness needs. 23 step 3 gives the
    publisher `github.com` and `api.github.com` and nothing else, so it gets its own
    network, its own proxy, and its own allowlist, generated beside the workers' one.

## Where this differs from the specification

These are deviations, not interpretations. Each is small, and each is listed again under
proposed spec changes.

- **`head_diverged --recollect-->`.** 09 draws this edge to `reported`. C4 re-enters at
  `scheduled` with a `correct` execution against the remote work branch. Going straight
  to `reported` would mean gates evaluated for a head with no completion claim, so
  `report_present` would fail and the only path forward would be a correction anyway.
  Re-entering at `scheduled` produces a claim for the new head and then runs the whole
  pre-PR path, which is what the surrounding prose asks for. The transition table gains
  `(head_diverged, scheduled)`.
- **A pull request closed unmerged.** 23 says it moves the task to `rejected`. 09's table
  draws that edge only from `ready_for_merge`, but a person can close a pull request at
  any point after it is opened, so the table gains the edge from
  `awaiting_external_review`, `external_feedback_received`, and
  `awaiting_ci_certification`.
- **`tasks.publish_pending` is dropped.** 09 says C4 replaces the flag with the
  `publishing` edge, and 14 marks the column "until C4". Migration 0007 drops it, and
  `TaskView` no longer carries it. `WakeReason.publish_pending` is gone with it.

## One path touched outside the phase's allowed set

`tools/smoke/compose_smoke.py` gained the attestation flag on its
`crucible-admin repository register` call. The default policy requires an external
review round, so registration without the operator's attestation is refused (23), and
the shared compose smoke registers `example-service` with that policy. The alternative
was to weaken the attestation rule to keep a smoke test passing, which is the wrong way
round: the smoke stack is the operator's own, so the smoke attests. Seven lines, one
call, no behaviour of its own.

## The live GitHub tier

`make e2e-github`, local only, never in CI. It needs three values, all of them paths or
a repository name, none of them a secret:

```sh
make e2e-github \
  CRUCIBLE_GITHUB_APP_JSON=<path to the App record> \
  CRUCIBLE_GITHUB_APP_KEY=<path to the App private key> \
  CRUCIBLE_GITHUB_TARGET_REPO=<owner>/<throwaway> \
  DOCKER='<the rootless daemon wrapper from README.md>'
```

What it does: seeds a local bare mirror of the target's default branch with the
operator's own `gh` credentials, read-only (the one place they are used, and the reason
is decision 8); registers the repository; runs a script-harness task to a collected head;
records an internal review; accepts; and lets the supervisor publish. It then asserts the
remote branch, the pull request, and the head all agree, merges that one pull request
with the App token as a **test-only act**, and observes the merge.

Crucible has no merge endpoint and never will: merging is the operator's act (23). The
merge call lives in `tests/e2e/github_live.py`, in the test tier, and reaches the
transport directly so that it cannot be mistaken for a product capability.

Cleanup closes every pull request the run opened and deletes every branch it created. It
refuses to delete `main`, `master`, or anything under `release/`, in the client as well
as in the tier, and the cleanup's own errors fail the test rather than being swallowed.

## Proposed specification changes

1. **09, the `recollect` edge.** Draw it to `scheduled` (a `correct` execution against
   the remote work branch), or say explicitly that a recollected head is expected to fail
   `report_present` and reach Foundry through `pre_pr_gates_failed`.
2. **09, a pull request closed unmerged.** The transition table needs the `rejected` edge
   from every observed state, not only from `ready_for_merge`, because 23 already says a
   close rejects the task.
3. **14, the API-writable tables.** `github_deliveries` is written by the webhook
   endpoint and belongs in 14's list of what the API role writes.
4. **14, the fenced tables.** `pull_requests`, `pull_request_heads`,
   `external_review_cycles`, `external_reviews`, `review_comments`, `reactions`, and
   `ci_certifications` are the supervisor's alone and are fenced; 14's list should name
   them.
5. **14, a new table.** `external_review_cycles` is not in 14's table list. 23 requires a
   cycle row per published head, so the table should be named there.
6. **10 and 17, the event principal.** An event about a webhook delivery is recorded
   under the principal `github`. 10 assumes every non-API event is `crucible`; it should
   name the third case.
7. **23 step 3, the token hand-over.** Replace "`docker cp` into the tmpfs" with stdin
   delivery through the Docker API attach stream, as S10 follow-up 1 asks. The socket
   proxy must permit `POST /containers/{id}/attach`, which the reference image does with
   `CONTAINERS=1` and `POST=1`.
8. **23 step 3, the publisher's repository.** "A fresh clone from Crucible's bare cache"
   should be "a repository built from the bundle", which is what removes the cache from
   the credential-holding container's reach entirely.
9. **12, the installation-token pattern.** S10 follow-up 2: the redaction pattern is
   `ghs_` plus at least 20 characters from `[A-Za-z0-9._-]` with no upper bound. It is
   implemented and tested; 12 should state it.
10. **23, the push remote.** 23 assumes the registered url is both what Crucible clones
    and what it pushes to. It should say that the push remote is derived from the
    repository's `owner/name` and that the registered url is the fetch source, so a
    deployment can point the fetch at a mirror without a credential in a worker.
11. **05b, `external_review.components`.** The seeded default policy carries
    `components: ["code"]`; a repository running code and security review sets both. No
    change needed, recorded here because the cycle logic depends on it being present.
12. **04, `GET /tasks/{id}/pull-request`.** The response also carries the review cycles
    and the reactions, which 04's one-line description does not mention.
13. **23, `neutral` and `skipped` conclusions.** 23 says green means every member
    concluded `success`, and the code now matches that exactly. GitHub uses `neutral` for
    a check that ran and declined to judge and `skipped` for one a condition excluded,
    and a repository that skips a required check on an unrelated path would sit in
    `pending` until the timeout. If that is not the intent, 23 should say which
    conclusions count as green; until it does, the strict reading is what ships.
14. **23, the closer.** "A PR closed without merge moves the task to `rejected` with the
    closer recorded" needs a second call: `GET /pulls/{n}` has `merged_by` but no closer,
    and the actor is on the issue events timeline. 23 should name the endpoint, and say
    that a repository whose timeline the App cannot read records the close with no actor
    rather than failing.
15. **05b, `external_review.accepted_signals`.** The default is now
    `["reaction:+1", "review"]`. A `comment` cannot be a round by default, because the
    provider's summary comment arrives before any verdict and is edited in place (23
    already says it never counts; the default list contradicted that).
16. **23, the publisher's network.** Step 3's allowlist of `github.com` and
    `api.github.com` is narrower than the workers' proxy permits, so the publisher needs
    its own egress network rather than the workers'. 23 implies it; it should say it.

## Limitations

- No live external review round was exercised in this phase: the reviewer's automatic
  round on the throwaway repository takes about 100 seconds (S12) and the live tier does
  not wait for it. The reaction path is covered end to end against the fake server, in
  both the 200 and the 403 shapes, and against the recorded shapes S12 measured.
- The live tier's target repository has no CI of its own, so its policy sets
  `ci_certification.allow_no_ci: true` and the live certification is `skipped`. Green,
  failure capture, and the `ci-decision` paths are covered against the fake server. The
  repository does get a check *suite* from an unrelated org-wide App on every head, which
  is what decision 21 is about: recorded, never required.
- The live tier's default policy sets `external_review.required_rounds: 0`, so the
  ordinary run exercises publication, observation, certification, and the merge without
  waiting on the provider. Issues read is now granted, so a real round *is* observable:
  `CRUCIBLE_GITHUB_WAIT_FOR_REVIEW=<seconds>` turns on a test that publishes and waits
  for the provider's own round, which S12 measured at about 100 seconds. It is opt-in
  because it makes the tier take minutes rather than seconds and because a quiet
  reviewer would otherwise fail a run about something else.
- The publisher's absence proof at the live tier scans what is still readable after the
  container is gone: the events, the database, and the publisher's output directory. The
  in-run `/proc` sampling and the `docker export` walk that S10 performed are that
  spike's evidence, not this tier's.
- `workflow_run_logs` keeps the first bytes of whatever the Actions endpoint returns,
  which is a zip. The excerpt is a pointer for a human, not a parsed log. (Replaced by
  `ci_failure_log` in FDY-0139: the tail of the failed job's plain-text log, through
  GitHub's redirect; see delivery-no-stall.md.)
- Webhook deliveries are matched to a pull request by number within the observed set. A
  deployment serving several repositories through one endpoint would want the repository
  in that match; the record carries it, and the matcher should use it before C5.

## Follow-ups

1. Use the delivery's repository as well as its number when matching a webhook to a
   pull request.
2. `probe-review` (`POST /admin/repositories/{name}/probe-review`, 23) is not
   implemented; the attestation and the first real task's signal are what a repository's
   record carries today.
3. The ready-for-merge wake carries the summary 23 asks for as prose. A structured
   payload would let Foundry render it without parsing a sentence.
4. The `draft` flag cannot be changed on an existing pull request through the REST API,
   so a reused one that is a draft is refused rather than converted. GraphQL has
   `markPullRequestReadyForReview`; whether Crucible should use it is a question for 23.
